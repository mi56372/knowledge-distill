# Pack 模式（多来源 / 大量判断时刻时改用这个）

当满足任一条件时，从 single 升级为 pack 输出：

- 素材包含多个来源（多本书、多门课、仓库 + 文档组合）。
- 判断时刻超过 15 条，单文件 SKILL.md 预计超过 400 行。
- 蒸馏出的能力彼此独立、各有明确触发场景，用户会在不同任务中单独调用。

## 产物结构

```
<output>/
├── SKILL.md                 # 路由入口：只含 ACTION REQUIRED + 分诊表（信号 → 子能力）
├── references/<cap-1>.md    # 能力 1 详解（完整流程 + 证据账本 + fallback）
├── references/<cap-2>.md    # 能力 2 详解
├── scripts/                 # 能力显式声明的确定性脚本（可选）
└── distill-state.md         # 状态文件（断点续跑用）
```

## 入口数与判断时刻的关系（两个阈值不要互推）

- **判断时刻数**决定"要不要 pack"（>15 条 → pack）。
- **入口数**由补丁 G 的 K3 晋级门决定（软预算 8：1 个路由入口 + 晋级子能力数）。
- 规则多不等于入口多：15 条以上规则通常只对应 2–4 个入口；反过来，规则只有 5 条但如果彼此独立可单独调用，仍可拆 2–3 个入口。**禁止按规则条数硬拆入口凑数。**

## 多来源冲突登记（多本书 / 多课程 / 多版本说法不一致时）

不要擅自择一，登记下来再处理：

| 主题 | 来源 A（定位） | 来源 B（定位） | 冲突点 | 处理方式 |
|---|---|---|---|---|
| 示例：库存周转基准 | 《书 A》§5.2（p.143） | 《书 B》§3.1（p.97） | 一个用 90 天、一个用 60 天 | 并行保留两套阈值，产物写"当行业为快消时用 A，重资产时用 B" |

处理优先级：能按适用条件并存 → 并存；适用条件相同且互相矛盾 → 取更严或更可验证的一版，另一版标 Tentative 留档；无法判断 → 标 unknown 并写"两个来源冲突，需用户指定口径"。

## 路由入口纪律

- 入口 SKILL.md 只做分诊，不写具体流程；每个子能力在分诊表里必须有一行"信号 → references/<cap>.md"。
- 只有分诊表格行中的引用参与路由；正文或共享背景提到某个文件不等于声明子能力。表格支持行内链接与引用式链接（如 `[cap][cap]` + `[cap]: references/cap.md`）。
- 每个子能力文件自带：触发条件、停止条件、fallback、证据账本、未知项、自检六节——与 single 模式的完整要求一致，缺一不可。
- 只有分诊表指向的 `references/<cap>.md` 才按子能力六节校验；共享背景、术语表等资料不强制六节。
- 晋级克制：references/ 内某一块必须已具备独立触发条件与完整流程，才配成为子能力；质量优先于数量，禁止凑数拆分。
- 跨能力共享的术语、背景放入口的"共享背景"小节，各子能力文件不重复粘贴。
- 交付前用 `python "<knowledge-distill目录>/scripts/validate_output.py" "<产物目录>" --pack` 检查入口与分诊表引用的子能力文件；入口只要求 ACTION REQUIRED + 分诊表，子能力缺节或证据行、checkbox、fallback 内容不合规按 P1 报出。
- 安装 pack 产物时，dry-run 与正式安装命令都必须追加 `--pack`，否则安装器会按 single 六节契约误拒路由入口：
  - `python "<knowledge-distill目录>/scripts/install_skill.py" "<产物目录>" "<目标目录>" --dry-run --pack`
  - `python "<knowledge-distill目录>/scripts/install_skill.py" "<产物目录>" "<目标目录>" --pack`
  - 确认替换已有目标时追加 `--replace --pack`，并记录安装器输出的 `BACKUP` 路径。

## 何时不要用 pack（fallback）

- 素材单一来源且判断时刻少 → pack 是过度工程，路由层只会增加一次无意义跳转，退回 single。
- 用户明确只要一个单文件 → 尊重要求，超长内容用 references/ 渐进披露解决，不拆入口。
- 各"能力"之间共享大量上下文、单独调用意义不大 → 拆开后每个子文件都读不懂，退回 single。

## 停止条件

- 分诊表中每个子能力都能独立命中至少一个真实用户请求，且每个都有完整自检 → 停止拆分。
- 出现"这个子能力只为了分类好看"的念头 → 立即停止，合并回去。
